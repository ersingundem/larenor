## Source-proven ordering defect

The acceptance handshake waits for the host to discover/open the virtual gamepad before dispatching its first OSC event. Pinned Moonlight's OSC uses `ControllerHandler.defaultContext`; its `GenericControllerContext.sendControllerArrival()` is a no-op, while `reportOscState()` sends the first multi-controller packet only when the visible OSC control is touched. Pinned Sunshine creates a virtual gamepad only on a controller-arrival packet or, as a legacy fallback, on the first active multi-controller packet. Therefore no owned evdev node can exist when host `OwnedGamepadAccess.arm()` polls before the first OSC dispatch. The ten-second discovery timeout produces the observed generic `GamepadHostFailure`, which the phase reducer currently publishes as `unclassified`.

The smallest correction is test/fixture-only: use the same visible production OSC control once as a bounded prepare event before `gamepad_ready`, then let the host discover the exact new device, grant/open/drain it, acknowledge `gamepad_armed`, and dispatch a second visible A down/up for the mandatory BTN_SOUTH+SYN witness. Bind the prepare/armed/effect order to the existing nonce and reject replay. This preserves the real effect requirement; only the second post-arm event may satisfy it. Add a regression showing arm-before-first-controller-packet fails while prepare→arm→second-effect succeeds. Also give `GamepadHostFailure` a closed discovery-timeout category so a future kernel/ACL failure is distinguishable without exposing device identities.
